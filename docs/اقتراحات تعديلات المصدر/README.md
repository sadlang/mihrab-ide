# اقتراحاتُ تعديلاتِ المصدر — ما يجب أن يدعمه المنبعُ أصالةً لنتخلّى عن رُقَعنا

> **الغرض.** كلُّ رُقعةٍ في محراب دَينٌ: تُطبَّق على مصدرٍ لا نملكه، وتنكسر متى انجرفت
> مرساتُها، ويجب أن تُراجَع مع كلّ ترقيةِ إصدار. هذا التقريرُ يقلب النظرَ إلى الجهة
> الأخرى: **ماذا لو دعم المنبعُ الميزةَ أصالةً؟** لكلّ رُقعةٍ هنا: أينَ تُطبَّق، وما
> الشكلُ المنبعيُّ الذي يُغنيها، وهل يُسقطها ذلك كلَّها أم بعضَها.
>
> **قاعدةُ التحديث.** كلُّ رُقعةٍ جديدةٍ تُضاف إلى محراب ⇒ سطرٌ في الجدول **و** قسمٌ
> مفصَّل هنا. رُقعةٌ بلا مقترحٍ منبعيٍّ = دَينٌ بلا خطّةِ سداد.

## م-١) اتّجاهٌ منطقيٌّ لقشرة workbench

**الحالُ في المنبع.** لا يدعم VS Code واجهةً من اليمين. لغاتُ الحزم العربيّة والعبريّة
تُترجِم النصَّ ويبقى التخطيطُ يسارًا. فما نفعله ليس «تفضيلًا» بل سدُّ نقصٍ كامل.

**ما تفعله رُقَعنا.**

| الرُقعة | الملفّ المنبعيّ | التعديل |
|---|---|---|
| `patch_workbench_rtl` | `vs/workbench/browser/workbench.ts` | `dir="rtl"` على `.monaco-workbench` + استيرادُ ورقتنا |
| `patch_menubar_rtl` | `vs/base/browser/ui/menu/menubar.ts` | المنسدلةُ تُثبَّت بحافّتها اليمنى بدل `style.left` |
| `patch_menu_rtl` | `vs/base/browser/ui/menu/menu.ts` | اتّجاهُ التعاقب الفرعيّ + **قواعدُ CSS داخل `getMenuWidgetCSS`** لأنّ القوائم في Shadow DOM |
| `patch_splitview_rtl` | `.../splitview/splitview.ts` | إزاحةٌ تراكميّة بـ`right` بدل `left` |
| `patch_sash_rtl` | `.../sash/sash.ts` | المقبضُ العموديّ بـ`right` |
| `patch_gridview_marker` | `.../grid/gridview.ts` | وسمُ `mihrab-grid-sv` لتمييز splitview الشبكة (تُدار بإعادة ترتيب العقد فلا تُقلَب) |
| `patch_tabsdrop_rtl` | `.../editor/multiEditorTabsControl.ts` | فهرسُ الإفلات والمؤشّرُ البصريّ — **عطبٌ وظيفيّ**: التبويب يهبط في مكانٍ خاطئ |

**المقترحُ المنبعيّ.**

1. **اتّجاهُ التخطيطِ إعدادٌ أوّليّ الدرجة**، يُحلّ في العمليّة الرئيسة مع اللغة:

   ```jsonc
   // product.json
   "layoutDirection": "rtl"          // أو يُشتَقّ من defaultLocale
   // settings.json
   "workbench.layoutDirection": "auto" | "ltr" | "rtl"   // auto ⇐ من لغة الواجهة
   ```
   ويُسنَد على حاوية workbench قبل بناء الأجزاء (نفسُ الموضع الذي نرقّعه).

2. **الخصائصُ الفيزيائيّةُ تُستبدَل بالمنطقيّة** في ودجات `vs/base/browser/ui`: ‏`left/right`
   ⇐ `inset-inline-start/end`، ‏`margin-left` ⇐ `margin-inline-start`، وهكذا. أكثرُ
   من نصف ورقتنا (‏٩٥١ سطرًا، قواعدُها مرقَّمةٌ حتّى ٣٥) ليس إلّا إبطالَ خصائصَ فيزيائيّةٍ
   مكتوبةٍ في المنبع.

3. **حساباتُ الموضع بـJavaScript تقرأ الاتّجاه**: ‏`splitview` و`sash` و`menubar`
   تحسب الإزاحةَ تراكميًّا من اليسار بافتراضٍ مبثوثٍ لا مُصرَّح. الشكلُ المطلوب:

   ```ts
   const rtl = getComputedStyle(this.el).direction === 'rtl';
   const edge = rtl ? 'right' : 'left';
   container.style[edge] = `${offset}px`;
   ```
   وهو ما نفعله حرفيًّا — لكن من الخارج.

4. **منطقُ الإفلات يفصل الجهةَ الفيزيائيّة عن الفهرس المنطقيّ**:
   ```ts
   // بدل: if (location === 'right') targetIndex++;
   const after = rtl ? location === 'left' : location === 'right';
   if (after) { targetIndex++; }
   ```
   هذا **إصلاحُ عطبٍ لا ميزة**: المنبعُ اليوم يخلط الفهرسَ بالجهة، وسيصير خاطئًا لديه
   في اللحظة التي يدعم فيها RTL.

5. **‏`getMenuWidgetCSS` تُولِّد قواعدَ الاتّجاه**: طالما القوائمُ في Shadow DOM، لا
   ورقةَ مستندٍ تبلغها. الاتّجاهُ يجب أن يُولَّد حيث يُولَّد باقي نمطِ القائمة.

**ما يسقط.** الرُقَعُ السبعُ كلُّها، ومعظمُ قواعد الورقة (تبقى قواعدُ الهويّة والطباعة).

## م-٢) اتّجاهُ النصّ في Monaco كخيارِ محرّر

**الحالُ.** بنيةُ Monaco الداخليّة إحداثيّاتٌ **فيزيائيّة LTR**. قلبُ الحاوية بـ`dir=rtl`
يُطيِّر النصَّ خارجَ الشاشة (قِسناه بـCDP على بناءٍ فاشلٍ أوّل). فالمحرّرُ يملك آليّةَ
سطرٍ RTL مدمجةً (`viewLine.ts` يضع `dir="rtl"` للسطر، والمؤشّرُ وhit-test يتبعانها)
**لكن لا خيارَ عامًّا يُشغّلها**: ‏`_getTextDirection` يُقرّر بمحتوى السطر وحده.

**ما نفعله.** ‏`patch_editor_rtl` على تسعة ملفّات: ‏`viewModelImpl` (اتّجاهُ السطر
افتراضيًّا RTL) · `margin.ts` (المزراب يمينًا) · `editorScrollbar.ts` (المحتوى) ·
`minimap.ts` (الخريطة يسارًا) وغيرها.

**المقترحُ المنبعيّ.**

```ts
// vs/editor/common/config/editorOptions.ts
textDirection: 'auto' | 'ltr' | 'rtl'   // auto = السلوكُ الحاليّ (من محتوى السطر)
```
يُستهلَك في ثلاثة مواضعَ لا أكثر:

```ts
// viewModelImpl.ts — نقطةُ القرار الوحيدة
private _getTextDirection(line: string): TextDirection {
  const opt = this._configuration.options.get(EditorOption.textDirection);
  if (opt !== 'auto') { return opt === 'rtl' ? TextDirection.RTL : TextDirection.LTR; }
  /* … السلوكُ الحاليّ … */
}
// margin.ts · editorScrollbar.ts · minimap.ts — التخطيط:
//   RTL ⇒ خريطة[0,mm] · محتوى[mm,mm+cw] · مزراب[mm+cw,W]
```
والحاويةُ تبقى LTR — هذا ليس التفافًا بل الصوابُ المعماريّ، وقد قِسناه.

**ما يسقط.** الرُقعةُ ذاتُ التسعةِ ملفّات، وقواعدُ الورقة ‏١·٧·١٣·١٤·١٥·١٦ (مسطرةُ
النظرة، التمريرُ اللاصق، ودجةُ الاقتراحات، الودجاتُ المُثبَّتة بـ`right` فيزيائيّ).

**الفائدةُ لغيرِنا.** كلُّ كاتبِ عربيّةٍ أو عبريّةٍ أو فارسيّةٍ في VS Code اليوم يحرّر
نصَّه في محرّرٍ يفترض أنّه إنجليزيّ. ومرجعُ التنفيذ عندنا كاملٌ ومُوثَّق:
[docs/rtl/monaco-rtl-map.md](../rtl/monaco-rtl-map.md).

## م-٣) لغةٌ افتراضيّةٌ للمنتج تُحلّ قبل أوّل رسم

**الحالُ.** حزمةُ اللغة لا تُفعَّل إلّا بعد أن يُسجّلها مسحُ الإضافات في
`languagepacks.json` — **بعد أوّل إقلاع**. فأوّلُ فتحٍ إنجليزيٌّ دائمًا، والثاني عربيّ.
ولا سبيلَ لتوزيعِ منتجٍ لغتُه الافتراضيّةُ غيرُ الإنجليزيّة.

وأثرٌ ثانٍ أخطر: خبزُنا للعربيّة يتجاوز حلَّ اللغة، فيبقى `configuration.nls.language`
غيرَ معرَّفٍ، ويكتب `setupNLS`:

```ts
let language = configuration.nls.language || 'en';
window.document.documentElement.setAttribute('lang', language);   // ⇐ lang="en"
```

فيصير المستندُ **يكذب**: واجهةٌ عربيّةٌ بالكامل و`<html lang="en">`. وهذا يكسر ثلاثةَ
أشياءَ لا تجميلًا واحدًا: نطقُ قارئات الشاشة (‏WCAG 3.1.1)، ومحدِّدُ `:lang(ar)` — الذي
مات صامتًا عندنا فعلًا (‏[AR-03]، اجتاز L0 وL2 وكان شيفرةً ميّتةً حتّى كشفه CDP)، وتلميحُ
اللغة لمحرّك تشكيل النصّ.

**المقترحُ المنبعيّ.**

```ts
// vs/base/node/nls.ts (أو main.ts:getUserDefinedLocale)
// أسبقيّة: --locale ← argv.json ← product.defaultLocale ← لغةُ النظام ← en
const locale = argvLocale ?? product.defaultLocale ?? osLocale ?? 'en';

// workbench.ts (مُمهِّد النافذة)
const language = configuration.nls.language || product.defaultLocale || 'en';
document.documentElement.setAttribute('lang', language);
document.documentElement.setAttribute('dir', getTextDirectionForLocale(language));  // ⇐ ومع م-١
```

وسطرُ `dir` هذا يُسقط شطرًا من م-١ كذلك: تصريحٌ واحدٌ في المُمهِّد أنظفُ من رقعةٍ
في `workbench.ts` وورقةِ أنماطٍ مستورَدة.

**ما يسقط.** ‏`patch_main_locale` و`patch_html_lang` كلتاهما. ويبقى `bake_nls_arabic`
مطلوبًا حتّى يدعم المنبعُ **حزمةَ لغةٍ مدمجةً تُحلّ في الإقلاع الأوّل** (م-٩).

## م-٤) عناوينُ الإعدادات المشتقّة حسابيًّا

**الحالُ.** عناوينُ لوحة الإعدادات ليست سلاسلَ مترجَمة: لا مدخلَ لها في NLS ولا في
حزمة اللغة. تُشتَقّ وقتَ التشغيل:

```ts
wordifyKey('editor.formatOnSave')  →  'Editor › Format On Save'
```

فيبقى في واجهةٍ عربيّةٍ بالكامل **سطرٌ لاتينيٌّ فوق كلّ إعداد** ووصفُه تحته عربيّ.
ولا طبقةَ أدنى تصله: لا سلسلةَ ترجمةٍ تتّسع له، ولا إعدادَ يخصّصه، ولا CSS تُصلحه
(النصُّ نفسُه إنجليزيّ — ليست مشكلةَ اتّجاه).

**عطبُ عزلٍ منفصلٌ يصيب المنبعَ نفسَه.** أيًّا كانت الترجمة، وضعُ عنوانٍ لاتينيٍّ داخل
فقرةٍ عربيّةٍ بلا عزلٍ ثنائيِّ الاتّجاه يُخرج النقطتين والفواصلَ إلى الجهة الخطأ. هذا
**عطبُ bidi في المنبع يصيب كلَّ لغةٍ RTL**، ولو لم يوجد محرابٌ أصلًا.

**المقترحُ المنبعيّ.**

```ts
// vs/workbench/contrib/preferences/browser/settingsTreeModels.ts
export function settingKeyToDisplayFormat(key: string, groupId = '', …) {
  …
  // 1) خطّافُ ترجمة: يسمح لحزمة اللغة/المنتج بتقديم صورةٍ مترجَمةٍ للمقطع
  const label = settingLabelProvider?.(trimmed) ?? wordifyKey(trimmed);
  // 2) عزلُ الاتّجاه في **النصّ** لا في CSS — لأنّه يُسنَد إلى aria-label ونصِّ الروابط
  return isRTLLocale ? `⁨${label}⁩` : label;
}
```

وبندان لا بدّ منهما مع أيٍّ منهما:

- **البحث**: بحثُ الإعدادات يطابق المفتاحَ والوصفَ و`keywords` ولا يطابق العنوانَ
  المعروض. فبلا إلحاقِ الصورةِ المعروضةِ بالكلمات المفتاحيّة، يقرأ المستخدمُ عنوانًا
  مترجَمًا ويكتبه **فلا يجد شيئًا**.
- **مسارٌ ثانٍ**: إعداداتُ الامتدادات ذاتُ `title`/`categoryLabel` لا تمرّ بـ`wordifyKey`
  أصلًا — فأيُّ حلٍّ في الاشتقاق وحده يترك نصفَ اللوحة خارجَه (وهذا حدُّ رقعتِنا
  المعلومُ اليوم).

**ما يسقط.** ‏`patch_settings_labels` ووحدةُ `mihrabSettingsLexicon.ts` وقاعدةُ CSS ‏٣٥،
ومعها **انحرافُنا المعلوم** في اختبار المنبع `settingsTreeModels.test.ts` (يتوقّع `'Foo'`
ويحصل على `'⁨Foo⁩'`).

**تغطيتُنا اليوم** — للسياق لا للمفاخرة: ‏٦٣٫٩٪ من مقاطع الفئات و٥٨٫٠٪ من عناوين
الأقسام، على ‏١٥٢٣ مفتاحًا محصودًا. الباقي إنجليزيٌّ عمدًا (أسماءُ أعلامٍ لا تُترجَم:
‏Git، Npm، Vite) بقاعدة «لا نصفَ ترجمة».

## م-٥) اسمُ مجلّدِ تهيئةِ المشروع قابلٌ للاشتقاق

**الحالُ.** المنبع يُصرِّح `FOLDER_CONFIG_FOLDER_NAME = '.vscode'` **مرّةً**، ثمّ يكتب
`'.vscode'` سلسلةً حرفيّةً في نحوِ ثلاثين موضعًا لا تمرّ بالثابت: إنشاءُ `tasks.json`،
ومسارُ `launch.json`، وتوصياتُ الامتدادات، وقصاصاتُ مساحة العمل، وتسميةُ `mcp.json`،
وتجاوزُ ترميز UTF-8، ونمطُ الموافقة التلقائيّة في الوكيل.

فتبديلُ الثابتِ وحدَه يُنتج أسوأَ حالة: **يقرأ من مكانٍ ويكتب في آخر**، بلا خطأٍ ولا
سجلّ. عطبٌ صامت. لذلك رقعتُنا في ستّةَ عشرَ ملفًّا.

**المقترحُ المنبعيّ.** ليس «اقبلوا `.محراب`» — بل:

1. **كلُّ موضعٍ يمرّ بالثابت.** إصلاحُ نظافةٍ مستقلٌّ عن أيّ منتج، ويُختبَر بحارسٍ
   ساكنٍ بسيط: لا سلسلةَ `'.vscode'` حرفيّةً خارج التصريح.
2. **الثابتُ يُشتَقّ من هويّة المنتج**:
   ```jsonc
   // product.json
   "folderConfigFolderName": ".محراب",
   "folderConfigFolderCompat": [".vscode", ".mihrab"]   // تُقرَأ ولا يُكتَب فيها
   ```
3. **دمجٌ بأسبقيّةٍ عند وجود أكثرَ من واحد** (`ConfigurationModel.merge`) فلا يضيع
   إعدادٌ صامتًا، و**الكتابةُ إلى الموجودِ فعلًا** فلا يكتسب مشروعٌ قديمٌ مجلّدًا ثانيًا.

**ما يسقط.** الرُقعةُ كلُّها ووحدتا `mihrabConfigFolder.ts` و`mihrabConfigFolderResolve.ts`.

**حدٌّ يبقى في الحالتين.** ‏`CachedFolderConfiguration` (مسارُ الاتّصال البعيد/الوِب)
يُخزّن المجلّدَ الأساسيَّ وحده، فأوّلُ إقلاعٍ بلا اتّصالٍ قد يفقد طبقةَ التوافق.

## م-٦) افتراضاتُ إعداداتٍ من هويّة المنتج

**الحالُ.** الحوارُ المشروط (احفظ/لا تحفظ/إلغاء) يحجب التطبيقَ كلَّه حتى يُجاب، وافتراضُه:

```ts
'window.dialogStyle': { 'default': 'native', 'scope': ConfigurationScope.APPLICATION }
```

فمحرابٌ على ويندوز — بلا إعدادٍ من المستخدم — يعرض حوارَ نظامِ التشغيل: نصُّه بلغة
ويندوز، اتّجاهُه LTR، وترتيبُ أزراره ليس ترتيبَنا. أشدُّ لحظاتِ الواجهة إلحاحًا (لحظةُ
فقدِ عمل) تخرج من التعريب كلِّه.

**جرّبنا الطبقةَ الأدنى وفشلَت — قياسًا لا ظنًّا**: ‏`configurationDefaults` من إضافةٍ
لا يغلب نطاقًا تطبيقيًّا (‏`APPLICATION`). نفسُ العيّنة مع الإضافة ردّت `0 حوار`، ومع
الإعداد في ملفّ المستخدم ردّت `1` بأزرارٍ عربيّة.

**المقترحُ المنبعيّ.** أن يُطبِّق المنبعُ `configurationDefaults` من `product.json`
بأسبقيّةٍ **فوق افتراضِ المنبع ودون تفضيلِ المستخدم**، وأن تشمل النطاقَ التطبيقيّ:

```jsonc
// product.json
"configurationDefaults": { "window.dialogStyle": "custom" }
```

> **غيرُ مقيس.** لم نتحقّق هل تدعم إصداراتٌ أحدثُ من ‏1.121 هذا الحقلَ في `product.json`
> ولا ما نطاقُه إن دُعم. إن ثبت أنّه مدعومٌ ويشمل `APPLICATION`، تسقط الرُقعةُ **فورًا**
> بلا حاجةٍ إلى مقترحٍ أصلًا — وهذا أوّلُ ما يجب فحصُه في هذا الملفّ.

**ما يسقط.** ‏`patch_dialog_style`، وكلُّ افتراضٍ تطبيقيٍّ نحتاج تغييرَه مستقبلًا.

## م-٧) حجبُ الجولاتِ المدمجة

**الحالُ.** الجولاتُ المدمجة (‏`Setup` · `SetupWeb` · `Beginner`) تُسجَّل برمجيًّا من
ثابتٍ مستورَد، ونقطةُ الامتداد **تُضيف فقط ولا تحجب**. فتزاحم جولةَ محراب على صدارة
أوّلِ سطحٍ يراه المستخدم، وتُبقي اسمَ المنبع وصوتَه الإنجليزيّ فيه.

وأقربُ بديلٍ من الطبقة الثانية — إخفاءٌ بـCSS — علاجٌ بصريٌّ يُبقي الجولةَ مسجَّلةً
وقابلةً للفتح من لوحة الأوامر.

**المقترحُ المنبعيّ.**

```jsonc
// product.json
"hiddenWalkthroughs": ["Setup", "SetupWeb", "Beginner"]
```
تُرشَّح في `registerWalkthroughs` قبل التسجيل. ‏**بالمعرّف لا بـ`isFeatured`**: المعرّفاتُ
ثابتةٌ عبر الإصدارات، والعَلَمُ يتبدّل — ولو رُشِّح بالعَلَم لسقطت `SetupAccessibility` معها،
وهي محتوى وصولٍ لا يُعوَّض.

**ما يسقط.** ‏`patch_walkthroughs_drop`.

## م-٨) ترويسةُ صفحةِ الترحيب من هويّة المنتج

**الحالُ.** الترويسةُ مبنيّةٌ برمجيًّا بـ`dom.$` لا قالبًا، والعنوانُ الفرعيّ
(«‏Editing evolved») سلسلةٌ في الشيفرة. فلا سبيلَ من إعدادٍ أو ورقةِ أنماطٍ لإضافة عنصر
شعارٍ أو تبديلِ الجملة.

**المقترحُ المنبعيّ.**

```jsonc
// product.json
"welcome": { "tagline": "…", "markAsset": "resources/welcome-mark.svg" }
```
مع عنصرَي DOM فارغَين مُسمَّيَين في الترويسة (`.welcome-mark` و`.welcome-pattern`) يملؤهما
المنتجُ أو يتركهما — فتصير الزخرفةُ والشعارُ ورقةَ أنماطٍ لا رقعةَ شيفرة.

**ما يسقط.** ‏`patch_welcome_rtl`؛ وتبقى قواعدُ الورقة ‏١٧·١٩·٣٢·٣٣ (وهي هويّةٌ بصريّةٌ
لا رقعةَ منبع، ومكانُها الصحيح ورقةُ أنماط).

## م-٩) تراكبُ ترجمةٍ للامتدادات المدمجة

**الحالُ (اكتُشف بتحقّقٍ حيٍّ بـCDP).** حين تكون حزمةُ اللغة نشطة — وهي كذلك دائمًا في
محراب — تحلّ النواةُ ترجمةَ بيانِ الامتداد هكذا:

```ts
const id = `${publisher}.${name}`;
const c = nlsConfig.translations[id];
if (c) { values = read(c).contents.package; }        // ⇐ مسارُ حزمة اللغة
else   { values = read(`package.nls.${locale}.json`); }  // ⇐ ارتدادٌ فقط حين لا حزمة
```

أي أنّ `package.nls.<locale>.json` **يُتجاوَز كلّيًّا** لأيّ امتدادٍ مُدرَجٍ في خريطة
حزمة اللغة. فمن أراد إكمالَ تغطيةٍ ناقصةٍ (حزمةُ ‏1.85 تغطّي نحوَ ٢٣٪ من مفاتيح البيان)
اضطُرّ إلى إعادة بناء `contents.package` كلِّه — وهو ما نفعله.

**المقترحُ المنبعيّ.** أن يكون الحلُّ **دمجًا بأسبقيّةٍ لا إحلالًا**:

```ts
values = { ...read(`package.nls.${locale}.json`), ...read(c).contents.package };
```
فيصير `package.nls.<locale>.json` تكميلًا مشروعًا للمفاتيح التي لا تغطّيها الحزمة، بدل
أن يموت صامتًا. وثانيًا: **حزمةُ لغةٍ مدمجةٌ تُحلّ في الإقلاع الأوّل** (لا بعد مسحِ
الإضافات) — تُسقط الحاجةَ إلى خبزِ الترجمة أصلًا.

**ما يسقط.** ‏`patch_extension_nls`، وجُلُّ `bake_nls_arabic` — ومعهما فخُّ الكاش
المعروف: مفتاحُ كاش الترجمة `md5(extId + version)` لا يتحرّك بإعادة البناء، فنضطرّ إلى
رفع نسخة `language-pack-ar` من بصمةِ محتوًى كي يُبطَل.

## م-١٠) اسمُ حزمة macOS يُحلّ لا يُفترَض

**عطبٌ صريحٌ في VSCodium.** ‏`build_cli.sh` و`prepare_assets.sh` يشتقّان مسارَ الحزمة من
`nameShort`، بينما يشتقّه مغلِّفُ vscode لـmacOS من **`nameLong`**. وهما في VSCodium نصٌّ
واحد فلا يظهر الفرقُ أبدًا؛ أمّا حين يختلفان (اسمٌ لاتينيٌّ قصير واسمٌ طويلٌ بلغةٍ أخرى)
فيبني المغلِّفُ `محراب.app` ويبحث السكربتُ عن `Mihrab.app`:

```
cp: .../VSCode-darwin-arm64/Mihrab.app/Contents/Resources/app/bin/mihrab-tunnel:
    No such file or directory
```

ويظهر **بعد ست عشرة دقيقة** من البناء، في آخر خطوة، بعد ترجمة CLI بـRust كاملةً.

**المقترحُ.** لا يُفرَض اسم — تُحلّ الحزمةُ الموجودة:

```sh
APP_PATH=$(ls -d "${OUT}"/*.app | head -1)
```
`ls -d` مصدرُ حقيقةٍ أصدقُ من أيّ اشتقاق، ويبقى صحيحًا لو غيّر المنبعُ قاعدةَ التسمية غدًا.

**ما يسقط.** ‏`patch_cli_macapp`. **جاهزٌ للرفع كما هو** — تصحيحُ سطرين، لا علاقةَ له
بمحراب، ويصيب أيَّ فرعٍ يُسمّي منتجَه بغير اللاتينيّة.

## م-١٣) إبرازُ المحارف الملتبِسة يُعادي العربيّة

ليست رُقعةَ مصدرٍ بل إعفاءً في `extensions/mihrab-shell/package.json` — ومكانُها هنا لأنّ
سببَها عطبٌ منبعيّ.

**الحالُ.** جدولُ `_common` في `vs/base/common/strings.ts` — **المدموجُ بلا شرطٍ في كلّ
محليّة** — يعدّ ‏٣٣ نقطةَ كودٍ عربيّةً «ملتبِسة»: الألف «ا» ⇐ `l`، والهاء «ه» ⇐ `o`،
والأرقامُ ٠١٥٧. وللمنبع استدلالُ سياقٍ يُعفي الكلمة، لكنّ شرطَه
**`!hasBasicASCIICharacters`** — أي أنّ **محرفَ ASCII واحدًا يُبطل الإعفاء كلَّه**.
ومعرّفاتُ ص تُكتب `نصاب_الفضة`، والشرطةُ السفليّة ASCII.

**القياس** (نفّذنا قاعدةَ المنبع حرفيًّا على مجموعاتٍ **مسمّاة**):

| المجموعة | النتيجة |
|---|---|
| نواة نهلة (‏١٧٤ ملفّ ص) | ‏٧٧٬٦٩٠ من ‏٦٠٧٬٠١٨ كلمة = **‏١٢٫٨٪** |
| أمثلة مستودع اللغة | ‏٥٩ من ‏٨٤٣ = ‏٧٫٠٪ |

أي مستطيلٌ أصفرُ حول واحدةٍ من كلّ ثماني كلماتٍ في شيفرةٍ عربيّةٍ سليمةٍ تمامًا. وليست
العربيّةُ وحدَها: المحليّةُ `ar` **غيرُ موجودةٍ في جدول المحليّات أصلًا**، فـ`allowedLocales`
عديمُ الأثر لكاتب العربيّة.

**المقترحُ المنبعيّ.** أحدُ ثلاثةٍ، مرتَّبةً بالأفضليّة:

1. **مدخلُ محليّةٍ `ar`** (وفارسيّة وأردو) في جدول `strings.ts`، فتخرج حروفُ الكتابة
   نفسِها من الالتباس لمن يكتب بها — وهي بنيةٌ قائمةٌ لا جديدة.
2. **استدلالُ السياق يقاس بالكتابة لا بـASCII**: كلمةٌ أغلبُها عربيٌّ لا تصير مشبوهةً
   بشرطةٍ سفليّة. الشرطُ الحاليّ يُبطله فاصلُ كلماتٍ مشروعٌ في كلّ لغةِ برمجة.
3. **إعفاءٌ بالكتابة (‏script) لا بالمحرف**: ‏`"editor.unicodeHighlight.allowedScripts": ["arabic"]`.

**وعطبٌ رابعٌ منفصل: الإصلاحُ السريعُ فخٌّ للمستخدم.** حين يرى المستخدم مستطيلًا يعرض
المنبعُ «استثنِ هذا المحرف»، فتكتب `excludeCharFromBeingHighlighted` القيمةَ في
`ConfigurationTarget.USER` **عالميًّا وبلا `overrideIdentifier`**. وقيمةُ المستخدم
العالميّةُ تغلب افتراضَنا المحصورَ في `[sad]` **ذرّيًّا لا دمجًا** — فنقرةٌ واحدةٌ في ملفّ
‏md تُعيد المستطيلَ الأصفرَ إلى كلّ ملفّ ص إلى الأبد، ولا يعرف المستخدم ما الذي فعله ولا
كيف يعود. **المقترح:** أن يكتب الإصلاحُ السريع بنطاق لغةِ المستند الذي فُتِح منه
(`overrideIdentifier: languageId`)، لا عالميًّا. وهذا عطبٌ عامٌّ لا عربيٌّ: يصيب كلَّ من
يضبط هذا المفتاح لِلغةٍ بعينها.

**ما يسقط.** إعفاءُ التسعةَ عشرَ محرفًا عندنا، والحارسُ الساكنُ الذي يشتقّه من جدول
المنبع كي لا يبيت. ونحن **لم نُطفئ** `ambiguousCharacters` ولا `invisibleCharacters`:
الإعفاءُ بالاسم يُسكِت الضجيجَ ويُبقي حمايةَ trojan-source، وهذا ما نطلب من المنبع
تعميمَه — لا إسقاطَ الحماية.

- **الأرقامُ تُنسَب إلى مجموعتها.** نسبةٌ بلا مجموعةٍ مسمّاةٍ ادّعاءٌ لا قياس.
- **ما لم يُقَس يُقال إنّه لم يُقَس** — كما في م-٦ أعلاه.
- **سابقةٌ قبل الرفع، ورقمٌ بعده.** يُسجَّل بحثُ السابقة (وُجد بلاغٌ؟ ما حالتُه؟) **قبل**
  الرفع لا بعده — تسجيلُ الرقم وحدَه بعد الرفع يترك أغلى خطأٍ بلا حارس.
